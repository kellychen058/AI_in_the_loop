Section 1 — What AI tools we plan to use, and what we will use each for
We will use Claude for planning, including clarifying requirements, breaking down tasks, and comparing design options. The team will make the final decisions.
We will use Matt Pocock’s skills to support this workflow: /grill-me to challenge assumptions, /to-spec to document agreed requirements and decisions, and /to-tickets to break the plan into tasks.
We will use Codex to implement the approved plan and write tests. Team members will review and test generated code before merging and write PR descriptions and decision records themselves.
API keys, credentials, and permission-related code and settings will be handled exclusively by team members, without AI access or modification.
We will use GitHub Copilot's inline autocomplete while typing — not as a substitute for writing the PR description or DECISIONS.md entry ourselves.
Section 2 — How we will document AI interactions
Our prompt engineering log will record prompts and models used for AI contributions included in the repo, noting what we kept or changed and why.
We will maintain an implementation log in each task ticket generated by  /to-tickets , linking relevant prompt entries and PRs and recording test results. Team members will verify it before merging.
One-off debugging questions or syntax lookups do not need separate entries unless their output contributes to code, text, or decisions included in the repo.
Section 3 — How we will handle disagreements about AI output quality
"If two engineers disagree about whether AI-generated code is good enough to merge, the code steward has final say — not whoever wrote the prompt, and not whoever has more experience."
"Evidence required before a merge decision: passes the existing test suite, passes the PR review checklist, and can be explained by someone other than whoever generated it."


## Week 12 revision — 2026-11-25

These three rules make the Week 3 requirements checkable from each PR. This revision was prepared with Codex assistance following the cross-team review; it requires human review before merge. It does not retrospectively certify earlier reviews or tests.

1. **Human-owned descriptions and contribution evidence.** Before merge, the responsible teammate must finalize the PR description: identify the AI-generated scope, what a human kept or changed and why (explicitly say if nothing changed), and the actual human confirming a significant decision. Remove placeholder text and link significant decisions to DECISIONS.md. Retrospective records must state when they were documented rather than being backdated. Maintain a per-member list of substantive code PRs and steward handoffs; documentation-only PRs do not satisfy CP2's substantive-code requirement. Evidence: merged PRs #22 and #25 retained human-review placeholders, and Week 12 feedback found uneven code contributions and missing decisions (follow-ups #27 and #28).

2. **Independent review with reproducible checks.** Each PR must identify the tested commit, commands, pass/fail/skip results, and who or what executed the checks. User-flow changes need at least one concrete action with expected and observed results. Before approving, a non-author reviewer must explain the main behavior and leave a substantive question, concern, suggestion or verification observation. Distinguish author-reported, agent-executed and personally repeated checks. An empty approval or model-generated score does not establish human understanding. Evidence: PR #18 has an approval without explanatory text; PR #25 includes model scores, which are not independent human review evidence (see also #26).

3. **Traceable AI use and evaluation boundaries.** Each PR must list the AI tool/model, instruction summary or spec link, generated files/functions, and subsequent human handling. Changes to product prompts or output parsing must include the same test input before/after, observed outputs, the revision and the re-run result; identify prompt changes separately from deterministic filters. Label mock/fallback, mocked-provider and live-provider evidence separately. Live results must name the date, exact model and tested commit; report skips and untested behavior honestly. Mark this revision evidence N/A with a reason when no product prompt/parser changes. Evidence: the received review identified skipped live tests and an injection fix implemented as a code filter; peer PRs x85432/AI-Intro#14 and #15 demonstrate concrete human edits and disclosed model failures (follow-up #29).
